# 情境子句稽核紀錄（clause-level audit）

> 對應 issue #42（由 #18 宣告 offline gate 通過前的雙軸 review 提出）。
> `tests/test_python_scenario_ledger.py` 機械檢查的是「`docs/test-scenario-ledger.md`
> 指向的測試存在且通過」。**它不檢查那些測試是否斷言該列宣稱的每個子句**——那是
> 人讀出來的判斷。本檔記錄那次閱讀怎麼做、結論是什麼，以及下一次要在什麼條件下重做。

## 稽核方法

對 inventory 的每一列，照下列順序做一次，不跳步：

1. **把該列拆成子句。** 用頓號、分號、「且」「並」「不得」切開，每個可獨立為假的
   斷言算一個子句。例如 V4「`keep_originals=1` 才保留 `original/`（原始檔與壓縮檔
   皆逐位保留）」是三個子句：預設不保留、帶旗標時保留、保留的是逐位元組的原檔。
   「才」這種排他詞一定是兩個子句，兩半都要驗。
2. **打開 ledger 指向的每個 test method，讀它的斷言，逐子句劃掉。** 只算真的會失敗的
   斷言：`assertIn` 一個必然存在的字串、或只驗檔案存在不驗內容，都不算劃掉。
3. **子句沒被劃掉時，二選一**：
   - 該行為其實有測試，只是 ledger 指錯 → 改指，並在覆蓋欄寫明哪個測試負責哪個子句。
   - 沒有任何測試斷言它 → 補斷言。優先補進已經跑起那條路徑的測試（省一次完整
     collect），只有在既有測試的前提互斥時才新增測試。
4. **子句在 Python 沒有等價物時，不要靜靜跳過。** 在覆蓋欄以「**對應關係**：…」開頭
   寫明 shell 的什麼對應到 Python 的什麼（或為什麼撤掉），讓讀者不必自己推測。
   已知的對應關係集中在：`CEPH_INCIDENT_QUIET`→`--quiet`、`--budget`→`--prom-timeout`、
   `--job-regex`→`--prom-job-regex`、`--allow-skip`→`--mode auto`、
   `--allow-cephadm-shell`／`--allow-kubectl-exec`／cephadm-shell runner／`toolbox-status`
   一律撤除。
5. **兩邊都不滿足該子句時，先確認 shell 參考實作。** 這是等價性 ticket，不是改善
   ticket：若 shell 也不做，那是共有的規則邊界，寫進覆蓋欄（見 V7），不要單方面改
   Python 的行為。

補完之後跑 `make validate`，必須離線全綠。

## 什麼時候要重做

`tests/test_python_scenario_ledger.py` 會把下表每一列的指紋和現況比對。指紋蓋住的是
這次閱讀的**兩邊**：

- inventory 那一列的**情境描述、fixture 手法與分類**——也就是子句從哪裡來。
  （不含 shell 行號：無關的編輯會讓行號漂移，一個沒人相信的過期訊號比沒有訊號更糟。）
- ledger 那一列的**狀態與「Python 覆蓋」欄**——也就是子句被誰回答。

所以：

- 改寫某列的描述、換 fixture 手法、或改分類 → 該列的稽核測試失敗，必須重讀該列
  （方法同上）、更新 ledger，再更新本表的指紋與稽核日期。
- 把某列改指向別的測試、或改寫覆蓋欄 → 同樣失敗。指向換了，上次「這些測試斷言了
  每個子句」的結論就不再成立，必須重讀。
- 新增 inventory 列 → 本表缺該列，測試失敗。
- 只是重新命名 Python test（ledger 同步改名）→ 覆蓋欄變了，本表也要一起更新；
  測試存在性則另由 `test_every_ported_scenario_points_at_tests_that_exist` 擋下。

指紋擋不到的一件事：ledger 指向的測試**內部**被削弱（有人刪掉其中一條斷言）而名稱
不變。那由 code review 與 `make validate` 的其餘部分負責，本表不宣稱擋得住。

重新產生指紋欄：

```sh
python3 tests/test_python_scenario_ledger.py --fingerprints
```
